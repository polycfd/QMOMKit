# Realizability

Realizability asks whether a moment sequence can come from a valid
distribution on a chosen support. For QMOMKit users, this is the question:

```text
Can these raw moments represent nonnegative distribution mass somewhere in
the allowed phase-space domain?
```

Not every list of numbers is a valid moment representation. For example, a
one-dimensional sequence with positive `m0` but a negative variance cannot
represent a physical distribution on the real line. A sequence may also be
valid on one support but invalid on another; moments that are possible on the
real line may be impossible if the variable must be nonnegative or bounded.

Realizability matters because QMOM and CQMOM reconstruct quadrature nodes and
weights from moments. If the moments are not mathematically consistent with a
valid distribution, quadrature reconstruction may fail or an evolved state may
need to be rejected before it is used.

## When Realizability Matters

Realizability can matter at several points in a QMOMKit workflow:

- initialization from explicit moments;
- moments generated by an external solver or data file;
- source-term updates during transport;
- accumulated roundoff or timestep error during evolution;
- enforcing physical supports such as size `>= 0` or a concentration in
  `[0, 1]`.

Distribution-based initialization usually produces consistent moments when
parameters are valid, but explicit moments and evolved moments should still be
checked when the workflow can approach the boundary of moment space.

## Explicit Checks

When a one-dimensional coordinate has a known support, `check_realizability(...)`
checks whether a raw moment sequence is consistent with that support:

```cpp
#include <qmomkit/realizability.hpp>

#include <iostream>

int main()
{
    const qmomkit::MomentSet moments{1.0, 1.0, 2.0, 6.0};

    const qmomkit::RealizabilityResult result =
        qmomkit::check_realizability(
            moments, qmomkit::MomentSupport::nonnegative);

    if (!result.realizable())
    {
        std::cerr << "Moments are not realizable: "
                  << result.message << '\n';
        return 1;
    }

    if (result.on_boundary())
    {
        std::cout << "Moments are realizable on the boundary.\n";
    }
}
```

The result reports:

- `status`: the realizability classification;
- `message`: a human-readable diagnostic;
- `checked_order`: the highest moment order included in the check;
- `failed_matrix`, `failed_matrix_order`, and `minimum_pivot`: diagnostics for
  failed or near-boundary checks.

The most useful statuses for users are:

- `strictly_realizable`: the moments are accepted away from the boundary;
- `boundary`: the moments are accepted but lie on the boundary of moment space;
- `not_realizable`: the moments cannot represent a valid distribution on the
  requested support;
- `invalid_input`: the request itself is invalid, such as empty moments,
  non-finite values, or an invalid bounded interval;
- `numerically_indeterminate`: the sequence is too close to the numerical
  tolerance to classify confidently.

`result.realizable()` is true for `strictly_realizable` and `boundary`.
`result.on_boundary()` is true only for boundary states.

## Support Constraints

Choose the support that matches the physical variable represented by the
moments. The support is part of the modelling assumption: a velocity component,
a particle size, and a bounded concentration can have different valid moment
spaces even when they have the same numerical moment values.

`MomentSupport::real_line` fits coordinates that may take any real value, such
as an unconstrained velocity component:

```cpp
const auto result =
    qmomkit::check_realizability(moments, qmomkit::MomentSupport::real_line);
```

`MomentSupport::nonnegative` fits coordinates that are zero or positive, such
as particle size, mass, or a count-like variable:

```cpp
const auto result =
    qmomkit::check_realizability(moments, qmomkit::MomentSupport::nonnegative);
```

`BoundedInterval` fits coordinates that stay inside a closed interval:

```cpp
const qmomkit::BoundedInterval support{0.0, 1.0};
const auto result = qmomkit::check_realizability(moments, support);
```

For bounded intervals, `lower` must be strictly less than `upper`.

## QMOM And CQMOM Status Handling

QMOM and CQMOM reconstruction also report whether a requested quadrature was
accepted.

For QMOM:

```cpp
const qmomkit::QmomResult qmom =
    qmomkit::compute_qmom(moments, node_count);

if (!qmom.ok())
{
    std::cerr << "QMOM failed: " << qmom.message << '\n';
}
```

A QMOM result with status `not_realizable` means the supplied one-dimensional
moment sequence could not be reconstructed as requested.

For CQMOM:

```cpp
const qmomkit::CqmomResult cqmom = qmomkit::compute_cqmom(cqmom_case);

if (!cqmom.ok())
{
    std::cerr << "CQMOM failed: " << cqmom.message << '\n';
}
```

CQMOM diagnostics can identify the phase-space dimension or conditioning step
where reconstruction failed. Use those diagnostics to trace which part of a
multidimensional setup needs attention.

Explicit realizability checks are currently one-dimensional. In a CQMOM
workflow, use them for one-dimensional moment sequences when a support-specific
check is needed, and use CQMOM status and diagnostics for the full
multidimensional reconstruction.

## Runtime Policies

For source-term evolution, QMOMKit can use a realizability policy as an
acceptance check. This is useful when a source update may push moments outside
the physical moment space and you want the timestepper to reject candidate
states.

The configuration form is:

```text
[time_integration.realizability]
check_mode = final_only
support = nonnegative
accept_boundary = true
tolerance = 1e-12
relative_tolerance = true
```

Supported check modes are:

- `none`: do not install a runtime realizability acceptance check;
- `final_only`: check the completed source-step candidate;
- `every_stage`: check intermediate and final source-step candidates.

Use `none` for workflows where you only want explicit checks or status
handling. Use `final_only` when you want a practical guard on accepted source
updates. Use `every_stage` when intermediate source-step states must also stay
inside the allowed moment space.

`accept_boundary = true` allows states classified as `boundary`. Set it to
`false` if your workflow requires strictly realizable candidate states.

Configuration parsing creates a `RealizabilityPolicy`, but the application
decides where to use it. For a source update, adapt the policy to the
SSP-RK3 options:

```cpp
qmomkit::RealizabilityPolicy policy;
policy.check_mode = qmomkit::RealizabilityCheckMode::FinalOnly;
policy.support = qmomkit::MomentSupport::nonnegative;

qmomkit::MomentSourceUpdateOptions options;
options.ssp_rk3_options.accept =
    qmomkit::make_realizability_acceptance_predicate(
        policy,
        [](const std::vector<double>& state)
        {
            return qmomkit::MomentSet(state);
        });
```

For `every_stage`, use `make_realizability_stage_acceptance_predicate(...)`
and assign the returned predicate to `options.ssp_rk3_options.stage_accept`.

## Configuration Examples

Use `support = real_line` for unconstrained one-dimensional variables:

```text
[time_integration.realizability]
check_mode = final_only
support = real_line
```

Use `support = nonnegative` for variables that cannot be negative:

```text
[time_integration.realizability]
check_mode = final_only
support = nonnegative
accept_boundary = true
```

Use `support = bounded_interval` with bounds for interval-constrained
variables:

```text
[time_integration.realizability]
check_mode = final_only
support = bounded_interval
lower = 0.0
upper = 1.0
```

The repository includes a small configuration example at:

```text
examples/configuration/realizability_policy_nonnegative.qmom
```

## Practical Guidance

Start with physically meaningful moments of the number density function (NDF).
`m0` should carry the intended total number density. Mixing normalized
probability moments with unnormalized raw moments changes the mathematical
state being checked.

The support should match the variable. Particle sizes and masses are often
nonnegative; volume fractions or normalized coordinates may require a bounded
interval; velocity components may use the real line.

Generate or provide enough moments for the requested quadrature. Realizability
does not replace the QMOM/CQMOM requirement that the moment order must support
the requested node count.

Status values are part of the workflow. Failed reconstruction,
`not_realizable`, `invalid_input`, and `numerically_indeterminate` are signals
to inspect the moment source, timestep size, support choice, or input data
before accepting the state.

Expect boundary states in some physical workflows. A boundary state can be
valid, but it may indicate that the represented distribution has collapsed to
fewer effective points or is close to a constrained support boundary.
